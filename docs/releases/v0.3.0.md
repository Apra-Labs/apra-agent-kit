## What's new

### Durable human input

A run can now stop and ask a person — for approval, or for missing information — and carry on when
the answer arrives, even after a restart or on another machine. Completed work is never re-run.

A pause **does not block a worker**. The run saves a checkpoint, releases its worker and stops; the
answer starts a fresh run that rebuilds from the checkpoint. At the default
`dispatch.concurrency: 1`, an unanswered question no longer stalls the whole agent.

```js
// host.config.mjs
modules: {
  dispatch:   { enabled: true },   // required: a paused run needs somewhere to park
  memory: {                        // required: the checkpoint lives here
    checkpoint: { enabled: true, store: 'sqlite', dbPath: './memory/checkpoint.db' },
  },
  humanInput: {
    enabled: true,
    maxInterruptions: 10,        // per run
    staleAfterMs: 86_400_000,    // 24h — answer still counts, the person is warned
    expiresAfterMs: 604_800_000, // 7d  — treated as refused, the run settles
    sweepIntervalMs: 300_000,
  },
}
```

`HUMAN_INPUT_ENABLED=true|false` overrides the file.

**Five kinds of question**, batched so one interruption can carry a whole form:

| Kind | Answer |
|---|---|
| `approval` | `'approve'` or `'deny'` |
| `pick_one` | one option value |
| `pick_many` | an array of option values (`[]` means "none of these") |
| `text` | a non-empty string |
| `pick_one_or_text` | an option value, or `{ other: '...' }` |

**Approvals now work.** A tool with the `approve` guardrail policy used to be denied whenever no
`approvalCallback` was configured. With human input enabled, the guardrail now asks a person and
pauses the run. An adopter's own `approvalCallback` still takes precedence.

**Answering:**

- `POST /jobs/:id/input` with `{ batchId, answers }` — the answer is attributed to the
  authenticated caller, never to whatever the body claims.
- The `job-input` MCP tool, for agents and clients that drive the kit over MCP.
- The chat UI renders the question form and submits the answer.

A job waiting on a person reports `status: 'waiting_input'`.

### `ask-user` — questions the model writes itself

`ask-user` is a generic tool where **the LLM decides what to ask**. It looks at the request, works
out what is missing, and sends up to 10 questions in one interruption. Questions can be plain
strings (free text) or structured objects with `kind` and `options`.

It is registered in the kit's default registry and works in plan-execute, open-ended and inside
workflows (`askUser` is now passed through `executeWorkflow`).

### Checkpoints — one record for crash recovery and pause

The old run-state tier and the human-input snapshot are merged into **one checkpoint** per run,
written by both strategies and stored through the memory module. A crashed run and a paused run
resume the same way:

- the resume reproduces the exact prompt the run was given, including recalled facts and
  conversation context;
- answers replay in order, so a guardrail approval survives a resume;
- a resumed run stays on the strategy it paused on;
- paused time never counts against `timeoutMs`; tokens and iterations already spent stay spent.

The config block is now `modules.memory.checkpoint`. `modules.memory.runState` still works as an
alias.

### Azure Functions: state in the task hub

On Azure Functions, run state now lives in the **Durable task hub itself**, as Durable Entities —
one per run for the checkpoint, one per session for chat history, one per person for long-term
facts. Local disk on a Functions host is per-instance and ephemeral, so SQLite there could not keep
a checkpoint between invocations; the task hub is already provisioned, so this costs nothing extra.

- **The orchestrator drives the run loop**, one step per activity invocation, so a durable run is
  checkpointed between steps instead of running start to finish in one activity.
- **A pause ends the orchestration.** The output carries only a checkpoint key; the answer starts a
  new orchestration. Nothing is billed or replayed while a person thinks, and the 16 KB output cap
  no longer limits how long a run can get before it can pause.
- **Activity retry:** `dispatch.durable.activityRetry.maxAttempts` (env
  `DURABLE_ACTIVITY_MAX_ATTEMPTS`) retries a step activity after a worker recycle, deploy,
  scale-in or OOM. Default `1` keeps the previous behaviour. Every failed attempt is audited.

### Storage selection and optional stores

```js
dispatch: {
  store: { kind: 'auto' },   // sqlite on a VM, task hub on Functions
}
```

`auto` picks the right store per deployment. Set `kind` explicitly to override. Two optional
adapters ship:

- **Cosmos DB** for job state (`dispatch.store.kind: 'cosmos'`) — install `@azure/cosmos`.
- **SQL Server** for memory (`memory.*.store: 'mssql'`) — install `mssql`.

Neither is a dependency of the kit; each is loaded only when configured, and a missing package
fails at startup with a message naming what to install.

### Retention

Settled records are now archived and expired on a schedule:

```js
dispatch: {
  retention: {
    archive: { enabled: false, store: 'cosmos', when: 'on_settle' },
    expiry:  { afterDays: 30, mode: 'auto', graceDays: 1 },
  },
}
```

- **Archive** is off by default. A record whose archive copy failed is **never purged**; the next
  pass retries.
- **Expiry** clears settled records. `mode: 'manual'` (env `JOBS_RETENTION_MODE`) turns off the
  timer and gives operators `POST /jobs/purge`, with `dryRun`.
- On Functions, the purge of completed orchestrations skips paused runs while they can still be
  answered.

### Reversing work after a correction

When a person's answer changes a decision a run already acted on, the kit can undo the steps it
already completed. A tool opts in by declaring `undo: { mandatory, describe, run }`; a tool that
declares nothing cannot be undone. Steps are sorted into read-only, mandatory, optional (offered to
the person as one `pick_many` question) and not-undoable (disclosed, never reversed). Reversal runs
last done, first undone, and stops and reports on a failure rather than pressing on.

### One-command smoke test

```bash
npm run smoke        # scripted model, no token, ~30s
npm run smoke:live   # real Fleet + model, needs CLAUDE_CODE_OAUTH_TOKEN
```

Starts the host on a free port, waits for `/health`, runs the black-box e2e suite against it,
prints a summary and shuts everything down. Exits 0 on pass, 1 on fail.

### Offline human-input demo

```bash
node deploy/demo-scripts/human-input-demo.mjs
# → http://127.0.0.1:3000/chat
```

A stand-in model drives the demo travel tools so you can see questions and approvals without Fleet
or a token. Try `plan me a trip to Paris` (which Paris?) or `plan and save a Kerala trip` (an
irreversible step asks for approval).

## What's fixed

### `@apralabs` packages arrive with their dependencies

`npm ci --omit=dev` installs no `@apralabs` packages, and `ensureApralabs()` copies them from the
global install. It copied the packages but not their hoisted dependencies, so the integration tests
failed with `Cannot find package 'ajv'`. Copied packages now bring their dependencies with them.
Closes #70.

## What's improved

- **Clear startup refusals.** `humanInput` without `dispatch` warns and does nothing;
  `humanInput` without memory, or with a memory store that cannot be opened, refuses to start
  instead of failing at the first question. Errors never print connection strings.
- **Memory learns from answers, never from approvals.** The long-term learner extracts facts from
  answered questions ("travelling with two kids"), but a one-off "yes" to an approval is never
  remembered as a standing preference.
- **Terminal logging** for questions asked, answers received and runs resumed.
- **Budgets pause their clock** while a run waits on a person.
- **Tests:** 30 new test files for human input, checkpoints, Azure entities, activity retry and
  retention, plus `npm run test:human-input`, `test:checkpoint` and `test:memory`.

## Breaking changes

None. Every new module is off by default.

Two things to know when upgrading:

- **`modules.memory.runState` is now `modules.memory.checkpoint`.** The old name is still read as
  an alias; rename it when convenient.
- **The SQL Server and Cosmos stores need their driver installed by you** (`mssql`,
  `@azure/cosmos`). Projects that don't use them are unaffected.

## Known issues

- **[#89](https://github.com/Apra-Labs/apra-agent-kit/issues/89) — `Invalid Host` when the agent is
  reached by hostname or IP.** `comm/express.mjs` builds the MCP app with localhost-only Host
  validation regardless of `MCP_BIND_HOST`, so a VM or container reached as `http://agent-vm:3000`
  or `http://10.0.0.5:3000` refuses every request, `/health` included. `localhost` access is
  unaffected. The same issue hid this behind a green e2e CI job.
- **[#74](https://github.com/Apra-Labs/apra-agent-kit/issues/74) — approvals are anonymous without
  an authenticator.** With human input on and no `startHost({ authenticate })`, answers are
  recorded as `anonymous` and anyone who can reach `/jobs/:id/input` can approve. Inject an
  authenticator before exposing an agent with approvals.
