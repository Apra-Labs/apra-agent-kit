# Memory Awareness for Agent Builder & npm Template

**Date**: 2026-09-28
**Status**: Draft
**Depends on**: conversation context plan (`docs/plans/conversation-context-plan.md`)

## Problem

The memory system (long-term memory, run state, conversation context, memory
tools, FSRS-6 decay, dedup, preloading, store adapters) is fully implemented
in the kit but invisible to two critical developer-facing surfaces:

1. **`npm create @apralabs/agent-kit`** — the scaffold template that every
   new project starts from. It ships `host.config.mjs` with no `modules` block,
   a `.gitignore` that doesn't mention `memory/`, and a README that doesn't
   mention memory capabilities. A developer who scaffolds a project has no idea
   memory exists.

2. **The agent-builder skill** (`.claude/skills/agent-builder/`) — the guided
   interview → spec → plan pipeline. It never asks about memory needs, the
   spec template has no memory section, the kit-file-conventions reference
   has no memory documentation, and the build order doesn't include memory
   setup. A spec/plan generated by the skill will never configure memory.

After the conversation context feature lands (replacing working-context), the
gap widens — there's a third memory tier (conversation context) that also
needs representation in both surfaces.

## What this phase ships

1. **Updated npm scaffold template** — new projects get a `host.config.mjs`
   with a documented `modules` block that includes commented-out memory
   configuration, a `.gitignore` that covers memory DB files, and a README
   that mentions memory as a capability.

2. **Updated agent-builder skill** — the interview asks about memory needs,
   the spec template includes a Memory section, the kit-file-conventions
   reference documents all memory-related files and configuration, and the
   build order includes memory setup.

3. **Updated getting-started guide** — the config reference and example
   include memory module documentation.

## Design principles

1. **Show, don't force.** The template's memory config is commented out so
   new projects don't get memory by default — but developers see it exists
   and know what to uncomment.
2. **Interview drives the spec.** If the developer says "no memory needed"
   during the interview, the spec and plan omit memory entirely. If they say
   yes, the spec includes full memory configuration and the plan includes
   memory setup tasks.
3. **Conversation context included.** After the conversation-context feature
   lands, all three tiers (conversation context, run state, long-term) appear
   in the template, conventions, and interview options.
4. **One source of truth.** The kit-file-conventions reference is the
   authoritative documentation for memory files/config. The spec template
   references it; the plan references it. No duplication.

## Memory (optional)

The kit includes a three-tier memory system. Uncomment the `memory` block in
`host.config.mjs` to enable:

| Tier | What it does |
|------|-------------|
| **Conversation context** | Carries prior chat turns across tasks within a session |
| **Run state** | Crash recovery — resumes interrupted tasks |
| **Long-term memory** | Cross-session facts with FSRS-6 decay |

When long-term memory is enabled, the agent gains four tools: `remember`,
`recall`, `forget`, and `promote`. See [docs/getting-started.md] for details.
```

## 2. Agent-Builder Skill Changes

### 2a. `SKILL.md` — Phase 1 Interview

Add a new question to **Round 4** (currently "Workflow + Members"):

Rename Round 4 to **"Workflow + Members + Memory"** and add a third question:

> Q3: "Does this agent need memory across conversations?"
> Multiple choice:
> - **No memory** — each task is independent, no cross-conversation state
> - **Conversation context only** — remember what was discussed in this
>   chat session (e.g. "book the cheapest one" after a search)
> - **Long-term memory** — learn and remember facts across sessions
>   (user preferences, domain knowledge, patterns)
> - **Both** — conversation context + long-term memory

This determines whether the spec gets a Memory section and the plan gets
memory configuration tasks.

### 2b. `SKILL.md` — Phase 1 Grilling

Add memory-specific grilling signals:

| Wizard Signal | Ask About |

| Conversation context (Q7) | How long are typical sessions? How many turns? Should old context summarize or just drop? |
| Long-term memory (Q7) | What kinds of facts should it learn? Should it learn from user corrections? How much can it store before it becomes noise? |
| Both (Q7) | How do the two interact? Should conversation turns promote long-term facts? |

### 2d. `references/kit-file-conventions.md` — Memory sections

Add the following sections to the reference:

#### Memory Module Configuration

Document the `modules.memory` config shape with all three tiers:
- `conversationContext` — mode, store, maxRecentTurns, maxTotalTurns,
  compactionStrategy, answerMaxChars, decay
- `runState` — enabled, store, dbPath
- `longTerm` — enabled, store, dbPath, autoLearn, decay, dedup,
  recallLimit, maxEntries, preloadDir

#### Memory Tools

Document `host/tools/memory-tools.mjs` and `withMemoryTools`:
- Tools: `remember`, `recall`, `forget`, `promote`
- Schema for each (kind enum: domain, preference, pattern, procedure)
- How they auto-register when long-term memory is enabled
- `agentDescription` coaching patterns for memory-aware agents

#### Memory Stores

Document the three store adapters:
- `filesystem` — simple JSON files in `./memory/`
- `sqlite` — `node:sqlite` `DatabaseSync`, WAL mode
- `cosmos` — Azure Cosmos DB, lazy-loaded, partition key = id/sessionId

#### Memory Preloader

Document `host/memory/preloader.mjs`:
- Reads `.md` files from a configured directory
- Stores each as a long-term memory entry with kind `domain`
- Runs once on startup, skips duplicates

#### Conversation Store

Document `host/memory/conversation-store/`:
- Interface contract (`CONVERSATION_STORE_METHODS`)
- SQLite adapter — table schema, indexes
- Cosmos adapter — partition key = sessionId

#### Build Order Update

Update the build order to include memory:

```
1. Tools — no dependencies, pure Python scripts
2. Workflows — depend on tools, follow the triad pattern
3. Registry — imports workflows/tools, wires MCP interface
4. Host config — agentDescription, modules, strategy, **memory**
5. **Memory config** — conversationContext, runState, longTerm, preload dir
6. Tests — verify each piece with mock-fleet
7. Deployment — Docker, env vars, compose updates
8. Documentation — generate README.md from the spec
9. Session cleanup + integration test
```

#### agentDescription Tips Update

Add memory-specific tips:

```
- If memory is enabled, coach the LLM to use memory tools:
  "ALWAYS use the recall tool before starting a task to check for relevant
  prior knowledge. Use the remember tool to store useful facts you discover."
- If conversation context is enabled, the system prompt automatically
  includes prior turns — no agentDescription coaching needed for that.
```

### 3b. `docs/getting-started.md` — New section

Add a "Memory" section after "Choosing a strategy":

```markdown
### Memory (optional)

The kit has a three-tier memory system. All tiers are off by default.

**Conversation context** — the agent remembers what was discussed earlier in
the chat session. Enable it when your agent handles multi-turn conversations
where users reference prior results ("book the cheapest one").

**Long-term memory** — the agent learns facts across sessions (user
preferences, domain patterns). When enabled, the agent gets four tools:
`remember`, `recall`, `forget`, `promote`. Coach the agent to use them
via `agentDescription`.

**Run state** — crash recovery. If a task is interrupted, it resumes from
the last checkpoint.

```js
modules: {
  memory: {
    conversationContext: {
      enabled: true,
      mode: 'store',
      store: 'sqlite',
      dbPath: './memory/conversation.db',
    },
    longTerm: {
      enabled: true,
      store: 'sqlite',
      dbPath: './memory/memory.db',
      autoLearn: true,
    },
    runState: {
      enabled: true,
      store: 'sqlite',
      dbPath: './memory/run-state.db',
    },
  },
}
```
```

1. Implement conversation context plan (`conversation-context-plan.md`)
2. Implement this plan (memory awareness for template + skill)

`conversationContext` in the template/docs (not `workingContext`) — the old
